Append-only memory

Today the memory block is rewritten every time the model saves a patch. This design keeps a big snapshot still and appends small updates after it. The provider can keep the old prefix cached; only the new tail is read.

The only layout. The append checkpoint is unconditional; the old snapshot layout is preserved on the snapshot branch. The request shape, the update blocks, the commit window and the compaction tail are live; the code is in src/core/append.ts and buildAppendPlan.

The one idea: do not edit page 1. Add a sticky note at the end.

The snapshot is the page the model already knows. A patch becomes a small note after the turn that produced it. When the notebook is full, we make a new snapshot from the page plus all the notes, throw the notes away, and keep a short tail. That is compaction.

1. Why the current layout is expensive

Every request is rebuilt from three things: the memory document, the newest turns, and the current turn. The memory document is the first message, so the provider reads it first. When the model calls smart_context with a patch, the plugin merges the patch into the memory document and the next request sends a different page 1.

The provider's prefix cache is not magic. It remembers a prefix of the request. Change the first message and the prefix is broken, so the provider starts again from the top. The bigger the conversation, the more it re-reads.

Two more things rewrite page 1 today. The rendered memory block also carries ## Pending eviction and ## Undo. Archiving a turn or applying an undo changes the block even when the eight memory keys did not move. And the pinned host notices live in the system prompt, before the messages: a Plan/Build switch changes the system prefix too.

2. The new shape

The new request has a stable front and a moving end. The front is the system prompt and a memory snapshot. The end is the current turn and a small state note. Between them are completed turns and the updates they produced.

BlockWhat it isWhen it changes
system + POLICYThe standing instructions and the fixed pool limits.When the profile or the plugin version changes.
memory snapshotThe eight memory keys at the last freeze or compaction.At the first freeze, then only at compaction.
turnsCompleted turns, verbatim. The current turn is last.A new turn appends; a compaction keeps the newest compactKeepTokens (20k default).
updatesThe keys changed by a completed turn, with full values.Once, at the next user turn. Never rewritten.
tail stateMode, budget, pending eviction and undo, in one small note.Every request; it is at the end, so it is the only churn.

3. A patch, step by step

  1. The model calls smart_context with action:"patch" and only the keys that changed.
  2. The plugin merges the patch into record.memory, as it does today. The merged document is what read, stats and undo use.
  3. The plugin also appends one update entry for the turn. Multiple patches in one turn are coalesced into one entry.
  4. The update is not injected in the middle of the turn. The tool result already confirms the write. At the next user turn, the update is rendered once, after the turn that produced it.
  5. The model reads the snapshot first, then the updates in order. A later value for the same key wins; maps merge, lists replace, a cleared key stays cleared.

An update is data, not a diff the model has to decode. It shows the full new value of each key that changed:

<smart-context-update seq="7" turn="msg_abc">
goal: "fix login and add the regression test"
facts: {"login-flow": "the token is refreshed before the form renders"}
plan: [
  {"step": 1, "status": "done", "text": "reproduce the bug"},
  {"step": 2, "status": "active", "text": "add the regression test"}
]
</smart-context-update>

The snapshot still says the old goal. That is deliberate. The model is told, in POLICY, that the snapshot is the checkpoint and the updates after it are newer. If it needs the merged document, smart_context read returns it.

4. The shared pool

The two budgets are no longer separate walls. They share one pool. The memory allowance is a ceiling, not a reservation: if memory uses less, the working side may use the difference before the pool fills. The tail a fold keeps is its own fixed budget, compactKeepTokens (20k default), not that leftover — otherwise a big working share would keep almost everything and free nothing.

The trigger is a single number:

pool       = memoryTokens + workingTokens        // 20k + 50k
memoryFoot = snapshot + all updates              // what the request carries
workingFoot = the turns + the tail state note
compact when memoryFoot + workingFoot > pool

5. Compaction

Compaction is the one deliberate reset. A due note lists the turns that will leave and opens a commit window; the model has until the next prompt to write what matters into memory (or calls action:"compact" to fold sooner). The fold then makes the updates part of a new snapshot, clears the log, keeps the newest compactKeepTokens (20k default) of turns, and archives the rest immediately with their raw messages. Everything before the reset was append-only; after it, the cycle starts again.

What the model does, and what the plugin does:

StepWhoWhat happens
1. Pool is fullPluginAdd a “compaction due” note that lists the turns about to leave. Do not drop anything yet; the turn keeps running with full context.
2. Commit windowModelWrite any durable fact that is still only in the leaving turns into memory. action:"compact" folds sooner; otherwise the fold waits for the next prompt.
3. FoldPluginsnapshot = memory, updates = []. The merged document already contains every accepted patch, including the commits.
4. ResetPluginKeep the newest compactKeepTokens (20k) of turns, archive the older ones immediately with their raw files kept, rebuild the request.
5. No commit?PluginThe fold runs anyway at the next prompt. Nothing is lost: the leaving turns are archived raw and stay readable with recall/expand.
What compaction cannot do. The plugin can fold patches mechanically. It cannot read a conversation and decide which unpatched detail matters. That is the model's job, which is why the “compaction due” note exists. If the model ignores it, the mechanical fold still keeps everything that was written to memory.

Rebuilding the retained tail

Compaction already changes the snapshot, so the provider is going to re-read everything after it. That is the one moment when rewriting the retained tail is free. Use it.

Do not rebuild the whole turn blindly. The safe rule is: replace, never remove a tool result, and keep the newest result the model is waiting on.

PartAfter compactionWhy
reasoning in a completed turndropIt is scratch work; the conclusion is in the assistant text and memory.
reasoning in the current turnkeepSome providers need it to continue a tool loop; stripping it can break the turn.
successful write or edit resultreplace with the path and “ok”The diff was useful while editing; after the turn the file is the source of truth.
failed write or edit resultkeep the errorAn error is the next instruction; never summarize it away.
successful bash or shell outputexit code plus the last ~20 linesThe tail usually holds the summary; the middle is noise.
failed bash or shell outputkeep the failing linesSame reason: the error is the answer.
read, glob or grepkeep the newest; older duplicates become “read earlier”The model can re-read; the current answer is what matters.
a tool result with no error markera short confirmation, not a deleted resultA call and its result must stay paired; the host may reject an orphan.
user messages and assistant answerskeep verbatimThey are the contract, not tool chatter. Do not machine-summarize prose.

Two hard rules:

  • Never drop the newest tool result in the current turn. The model is waiting for it; without it the turn is broken.
  • Never change the shape. A text result stays text, a content array stays an array, a JSON result stays JSON. The host's prepare rejects the wrong shape.

What else is safe: drop empty parts, collapse duplicate notices, normalize whitespace in tool output, keep only the latest mode line, and dedupe refs by page and section. What is not safe: rewriting the user's words, mechanically shrinking the model's final answer, or deleting the raw archive. The archive is where recall goes; keep it raw.

The call input can be the bigger cost. A write call carries the whole file, which can be larger than its “ok” result. But the input is part of the assistant message; truncating it may break the tool schema. Leave the call alone in v1. If call inputs dominate, the v2 move is to replace the whole call-and-result pair with one synthetic work-log note, not to edit the input in place.
Measure before trusting it. A summarized edit result may make the model re-read the file, which can cost more than the diff. A summary of a successful test may hide the one warning that mattered. rebuildOnCompaction is that flag (off by default); a fold records rebuildSaved on the session record, so a real session can be compared with and without it. The conservative rules above are what ships; unknown tools are left alone.

6. The tail state note

The mode, the live budget, pending evictions and undo all need to be visible, but none of them belongs in the snapshot. They go in one small note at the very end, after the current turn.

<smart-context-state>
mode: plan — do not modify files; tell the user to switch agents
pool: 42k/70k (snapshot 8k · updates 4k · turns 30k)
pending: msg_123 (the login spike) · archive or purge it
undo: the previous turn was rolled back
</smart-context-state>

Why not put the mode in the header? Because a mode switch would then rewrite the header and reset the whole cache. The tail note is small and already regenerated every request, so adding the mode there costs nothing extra.

Why after the current turn, not before it? The note carries live numbers that change on every pass. Placed before the turn, a one-character change invalidates the whole turn and the provider re-reads it on every tool loop - measured live at 10-50k uncached tokens per pass. Trailing keeps the turn's bytes stable, the note still arrives before the model replies, and its first line (mode:) makes clear it is state rather than a new request.

7. What stays the same

  • The transcript is read-only. The plugin still rebuilds every request from the host's messages and the session record.
  • The tool and its actions do not change. read, patch, stats, ref, archive, purge, recall, expand and notice keep their shapes; compact is added.
  • The archive still catches what leaves. A turn dropped at compaction becomes pending, then archives under the same rules.
  • Subagents keep their own records. The snapshot and the updates are per session.
  • The snapshot carries no live numbers. The budget line lives in the tail note and in tool results, never in the checkpoint.

8. Trade-offs and open questions

Trade-offWhy it mattersMitigation
The request can grow to the pool limitToday the working window is capped at 20k; the new layout can send up to 70k before compacting. Cached input is cheaper, but not free.Measure total input and cached input. Let the user pick the pool size; keep the real model context as a hard ceiling.
The model must combine the snapshot and the updatesIf it reads an old value and misses a newer update, memory looks stale.Updates show full new values, not cryptic diffs. POLICY says “the newest value wins”. read returns the merged document. Compaction refreshes the snapshot.
The update log can growA patch every turn can cost more than the memory it describes.One update per turn, not per call. Compact on a size ratio as well as the total pool.
A mode switch must stay visibleDropping the live Plan/Build instruction caused a real bug: the model read a stale Plan notice and refused to edit in Build mode.Keep one compact mode line in the tail state note. Drop the history and the old nudges.
Undo can contradict the update logRestoring memory while old updates still say the undone values is wrong.Undo writes a fresh snapshot immediately and clears the log. Rare, and correctness comes first.
The host may prepare messages differentlyThe plugin controls event.messages, but the host builds the final request.Verify the turn-boundary update live, not only in the smoke test.

A simpler fallback

If the append-only log feels too heavy, keep the stable snapshot and put one current-state overlay at the very end, after the working turns. The overlay shows only the keys that differ from the snapshot, always with full values. It is rewritten on each patch, but it is the last thing, so the cache break is its own size, not the 70k header. It is less code and less risk; append-only is still better for cache because only the delta is new.

9. Rollout

  1. Branch from a clean main: feat/append-only-memory — done; it was merged into main and ships behind the flag.
  2. Append is the only layout; snapshot is preserved on the snapshot branch.
  3. Build the record split first: base, updates, merged memory. Old records load as base = memory, updates = [].
  4. Add the renderer and the byte-stability tests before touching compaction.
  5. Then the shared pool, the compaction protocol, and the tail state note.
  6. Measure stableTokens and changedTokens against the shipping layout on a recorded session. Flip the default only after the numbers say it is better.
