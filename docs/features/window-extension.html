Window extension - one bounded growth per era

Status: shipped - Read when: window.ts, decideExtension, effectivePoolCap, the windowExtend / windowExtendFactor / windowWarnPercent keys, action:"extend", the near-cap note, record.ext, "the window grew", or "the extension was refused".

What it does

The working pool can grow once per compaction era, on the model's request, when the trailing state note says the pool is near its cap. At windowWarnPercent (80% default) of the effective pool the note asks the model to write the continuation brief into memory first, then offers two moves: finish only the current atomic step with smart_context { action:"extend", reason:"..." }, or fold now with action:"compact". The extension is not automatic; the model has to ask for it and say why.

A grant raises the pool to a cap that is bounded twice: by windowExtendFactor (2 means double, clamped 1.1..4) and by what the host's own ceiling will accept before it compacts. The realized multiplier can therefore be smaller than the configured one. The cap that the plugin enforces - for the working window, budgetOf, /context and the stats report - becomes record.ext.toCap; the model's real context window is only a clamp and is never printed as a used figure.

One grant per era. A fold clears record.ext, and so does a host compaction, so the next era starts at memoryTokens + workingTokens again. After a grant the note reports the extension and asks for one atomic step; at the warning line of the extended pool it says the extension is spent and the fold runs at the cap; once the pool is full the usual compaction due line says the extension is spent. There is no automatic continuation after the fold.

How & why

The note always carries the denominator

The trailing state note used to print the pool cap only for windows under SMALL_WINDOW_MAX (300k). The model cannot make an extension decision against a bare numerator, so the gate is gone: the note now always prints pool: <used>/<cap> · <pct>% (...). The cap is the effective pool for the era - record.ext.toCap when an extension is live, otherwise memoryTokens + workingTokens. The percentage is a rounded display against the effective cap, and isNear uses the same cap; the rounding is clamped so a bad estimate cannot overflow the line.

The decision point

At or above windowWarnPercent of the effective pool, and below the cap, the note says:

window: <left> left (<pct>% of the pool used). Write the continuation brief into memory first (goal/plan/decisions/open, files, next steps), then choose:
  finish only the current atomic step: smart_context action:"extend" reason:"..." - or fold now: action:"compact"

When the extension is unavailable - disabled, already granted this era, or the model window is unknown - only the fold line is printed. A leaving at the fold: list follows when the fold is near or due.

The clamp arithmetic

baseCap = memoryTokens + workingTokens. With the model window window and the host's own system/tool estimate hostSystemTokens:

  • reserve = max(floor(window * 0.1), window >= 32000 ? 16000 : 0)
  • ceiling = window - reserve - hostSystemTokens
  • hardCap = floor(ceiling * 0.9) - the last 10% is safety for tool schemas and character-count error
  • toCap = min(floor(baseCap * clamp(factor, 1.1, 4)), hardCap)
  • grant only when toCap > baseCap; the stored factor is round(toCap / baseCap, 2)

The order of the refusals is deliberate: disabled, already extended, unknown model window, then no headroom. The last case is the one that surprises: a window small enough that the hard cap sits below the base pool refuses rather than shrinking the pool. hostSystemTokens is optional and is subtracted only when the host reports it.

What a grant changes

runMemoryTool requires a non-empty reason, calls decideExtension, stores record.ext = { at, turn, reason, fromCap, toCap, factor }, and clears a compact.due mark if one was set. It does not touch the transcript or the memory document. The next note says:

extension: +<n>% at turn <id> (<reason>); <left> left. Finish only the current atomic step and update the brief.

At the warning line of the extended pool it adds extension spent: ... Update the continuation brief now ... the fold runs at the cap. At 100% the compaction due line adds The extension is spent. A granted extension that is not spent does not remove the fold: the fold still happens at the extended cap.

Resets and what does not happen

action:"compact" clears record.ext with the rest of the fold state. A host compaction also clears it, along with windowStart, the update log, seenTurns and the rebuild bookkeeping; the host's turns are archived first. The plugin does not continue the task by itself after a fold, and it does not grant a second extension in the same era.

The adapter is a whitelist

createSmartContextTool copies each argument onto the request field by field; it is not a spread. A field declared in TOOL_INPUT and read by the core is invisible on the wire until it is copied there, and core tests that build a request object directly cannot see the gap. reason was declared and never copied, so every action:"extend" answered extend needs reason no matter what the model sent, and sessions folded instead of granting. When adding a field, add it in three places - TOOL_INPUT, the request object, and a smoke assertion that calls createSmartContextTool(...).execute(...). Pinned by “the adapter forwards reason to extend”.

Config keys / UI

KeyDefaultRange / effect
windowExtendtrueallow one working-pool extension per compaction era
windowExtendFactor21.1..4 - requested multiplier, further clamped by the model window
windowWarnPercent8050..95 - effective-pool percent that offers extend or fold

All three are profile-overridable session keys, like the budget and archive keys. The cap in the note is always the effective pool: pool 60k/300k · 20% before a grant, pool 60k/400k · 15% after one. The real model window appears only inside a refusal (no headroom under the ~810k model ceiling), never as a used figure.
