Undo - the record follows the host's revert

Status: shipped (v0.1.25) - Read when: /undo or /redo, session.revert.committed, the undo journal, or "memory still describes an undone turn".

What it does

  • Watches the host's event bus for session.revert.committed and queues its boundary on the session record; /redo before a prompt never queues anything, because only the committed event is read.
  • On the next context pass, applies the rollback before the window and the change detection run, so the same pass already speaks about the transcript the host kept.
  • Restores the memory document from an inverse journal, re-pins notices the model retired, and puts purged turns back.
  • Drops every tracked turn at/after the boundary from seenTurns, pending, archive and the pass history.
  • Tells the model once, via a ## Undo section of the memory block, that the rollback happened; /context adds last undo and undo journal lines.

docs/SPEC.md owns the user-visible behavior; this page owns the mechanism.

How & why

The host's revert

/undo calls session.revert.stage: files are restored and the prompt returns to the composer, but nothing is committed. The commit happens on the next prompt: the host looks the boundary message up by id, deletes every session_message row with a sequence at or after it (the boundary user message itself included), clears the revert, and emits session.revert.committed with { sessionID, to }. /redo calls session.revert.clear and emits nothing else, which is why a staged revert is deliberately ignored.

The boundary is a message id, and the host's ids sort by creation time (Identifier.ascending: timestamp then counter), so id >= to is "at or after the boundary" with no extra timestamp stored.

Queued, then applied in the pass

The event handler only calls queueRevert under store.mutate; the earliest boundary wins. The pass applies it, which keeps one place - the pass - in charge of the record order, and lets applyRevert run before selectWorkingWindow and the change detection. A bus the host does not hand over (no ctx.event) leaves the record alone; so does an event from another directory, guarded by sameDirectory.

One journal entry per turn

The record only holds the current document, so restoring a write needs an inverse captured before the write. noteTurn creates the entry at the top of every pass whose current turn differs, snapshotting pending before the pass can evict, age or auto-archive anything. A write fills its own fields lazily: memory stores the value each top-level key had before its first write of the turn (a second write to the same key does not overwrite the capture), notices the retired notice and its slot, purged the whole purged turn, raw messages included. Bounds: 8 turns and 40k characters, newest entry always kept; the oldest whole entry goes first.

What a rollback restores

Journal entries at/after the boundary unwind newest-first: memory keys, retired notices (un-retired by text, re-pinned at their slot), purged turns. Then the structure is rebuilt: pending becomes the boundary entry's snapshot, pulling raw messages back out of the archive for a turn the span auto-archived and restoring the snapshot's age; leftover pending/archive ids at/after the boundary are dropped, and seenTurns and history are filtered to id < to. The marker clears, the journal truncates, and lastUndo records what happened for /context.

The ## Undo line is rendered for the turn the rollback landed in only: lastUndo.seen holds that turn id, and noteTurn deletes the entry when a different turn arrives. Deterministic per record, so a retried pass renders the same bytes.

What it cannot restore

An archive trim is irreversible: trimArchive drops raw messages to hold the caps, and the journal does not keep second copies. A pending turn whose raw messages are gone cannot be rebuilt, and lost counts it instead of fabricating one. Writes from turns older than the retained journal are not rolled back. /context purge bypasses the journal (a known gap). And a host compaction that shortens the transcript never triggers a rollback: only the dedicated event does.
