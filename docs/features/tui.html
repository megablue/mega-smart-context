The TUI half - a status dialog and one update toast

Status: shipped (v0.1) - Read when: tui.ts, the mega-smart-context.status palette command, the status dialog, its RPC bridge (STATUS_RPC, stats, purge), src/core/status.ts, the update toast, "the command does not appear", "the server half did not answer".

What it does

  • One palette command, Context status (id mega-smart-context.status), opens a dialog.select: a memory bar, a working-window bar, turns kept and dropped, pending/archive/ref counts, the host-system size when the last pass measured one, then Resume and Purge a turn….
  • It pulls: one stats RPC when the command runs, and one refresh before the purge list. No render surface, no sidebar, no JSX, nothing on a timer.
  • Resume sends the plugin's cue through client.session.synthetic - the same channel as /context resume, so no user message and no new turn.
  • Purge lists the pending then archived turns, confirms, and deletes the chosen one through the server half. The deletion is journaled, so /undo can put it back.
  • The same entrypoint runs the once-a-day update toast, independently of the dialog. Its updateCheck key does not gate the command.

How & why

Why a dialog first (phase 0)

The sidebar slots (sidebar.content, session.panel) render JSX and therefore need @opentui/solid plus a jsxImportSource on this package. The dialog API needs neither, so phase 0 ships the same numbers through the host's own dialog.select: no dependency, no build step, and the command is a keymap registration that can be deleted without touching the record.

The two halves keep separate stores

The server half owns the record in the host's KV (plugin:<id>:session/<sid>). The TUI half's storage.store is a per-key JSON file under ~/.local/state/opencode/<channel>/tui/plugin.<id>.<key>.json - the update check writes one, and it is not the KV. The dialog therefore cannot read the record directly. It asks the server half over the host's plugin RPC: POST /api/rpc/mega-smart-context/stats, routed to the last registered definition with that id. Every loaded instance registers identical handlers; the config is global and the record is keyed by session, so which instance answers does not change the reply.

Pull, never render

The command runs rpc.stats once, then builds the rows; a render path never calls RPC, so an idle terminal makes no requests. Choosing purge re-reads the stats first: a pass between opening the dialog and choosing the row could have archived or purged a turn, and a stale id would only fail. The status rows are disabled so Enter lands on an action; Purge is disabled when both lists are empty. The title carries the loaded version; the three failure paths are dialogs, not throws: no session route, no RPC bridge, and an RPC error ("the server half did not answer").

One purge path, journal included

purgeWithUndo looks up both lists, removes the turn, then captures the vanished entry. The tool already did this; /context purge did not, so a later /undo could not restore it - the known gap. The dialog would have added a third unjournaled surface, so the sequence moved into one function and all three call it. The TUI handler saves through store.mutate, the same lock and cache the pass uses.

Traps

  • No default key is claimed: the id is the config key a user binds. The layer is mode: "global" so the palette finds it outside the prompt's base mode.
  • Only one dialog is active at a time. The flow is sequential (status select resolves, then the purge select opens); opening a second dialog from an actions footer would strand the first promise.
  • The RPC schema is Standard Schema v1, hand-rolled, so the plugin keeps no dependency on the host's schema library. The host validates input and output: a malformed request returns rpc.invalid_input with our own message, and a reply that drifts from StatsReply fails the call rather than reaching the dialog.
  • The host resolves the TUI entrypoint before anything else and loads it next to the server half; a first install can need a restart before the command appears. updateCheck:false still registers it.
