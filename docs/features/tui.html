The TUI half - a status dialog, a sidebar block and one update toast

Status: shipped (v0.1) - Read when: tui.ts, the mega-smart-context.status palette command, the status dialog, its RPC bridge (STATUS_RPC, stats, purge), src/core/status.ts, the sidebar.content block (src/tui/sidebar.tsx, src/tui/status-store.ts), the update toast, "the command does not appear", "the block does not appear", "the server half did not answer".

What it does

  • One palette command, Context status (id mega-smart-context.status), opens a dialog.select: a memory bar, a working-window bar, turns kept and dropped, pending/archive/ref counts, the host-system size when the last pass measured one, a line saying whether the sidebar is drawing, then Resume and Purge a turn….
  • It pulls: one stats RPC when the command runs, and one refresh before the purge list.
  • The sidebar block appends to sidebar.content, so it is the last item inside the sidebar's scrollable list (the panel's bottom edge would be sidebar.footer), and draws the same reply as five short lines plus [status] [resume] [purge]. It renders from an ephemeral per-session store that is filled by a pull, never by the render.
  • Resume sends the plugin's cue through client.session.synthetic - the same channel as /context resume, so no user message and no new turn. The click asks first; the dialog row does not.
  • Purge lists the pending then archived turns, confirms, and deletes the chosen one through the server half. The deletion is journaled, so /undo can put it back.
  • The same entrypoint runs the once-a-day update toast, independently of the dialog and the block. updateCheck and sidebar do not gate the command.

How & why

Why a dialog before a sidebar

The dialog API needs no dependency at all, so phase 0 shipped the same numbers through the host's own dialog.select. The sidebar slots render JSX and need @opentui/solid: they are phase 1, added on top of the same reply and the same RPC.

The two halves keep separate stores

The server half owns the record in the host's KV (plugin:<id>:session/<sid>). The TUI half's storage.store is a per-key JSON file under ~/.local/state/opencode/<channel>/tui/plugin.<id>.<key>.json - the update check writes one, and it is not the KV. The dialog and the sidebar therefore cannot read the record directly. They ask the server half over the host's plugin RPC: POST /api/rpc/mega-smart-context/stats, routed to the last registered definition with that id. Every loaded instance registers identical handlers; the config is global and the record is keyed by session, so which instance answers does not change the reply. The sidebar's mirror is the third store: storage.memory("sidebar"), ephemeral, one entry per session, gone when the TUI exits.

The sidebar is a mirror, not a meter

sidebarRefreshOf holds the pull rules: nothing for an empty id, nothing while that session's pull is in flight, nothing inside SIDEBAR_STALE_MS (15s) unless force, and nothing at all when the host has no RPC bridge. A failed pull keeps the last numbers rather than blanking the block. The store is bounded to MAX_SIDEBAR_SESSIONS (32) by dropping the oldest pull, so a TUI left open for days does not accumulate a record per session it ever showed.

Pull, never render

The command runs rpc.stats once, then builds the rows; the block's effect asks once per session and once per idle pass. A render path never calls RPC, so an idle terminal makes no requests. Choosing purge re-reads the stats first: a pass between opening the dialog and choosing the row could have archived or purged a turn, and a stale id would only fail. The status rows are disabled so Enter lands on an action; Purge is disabled when both lists are empty. The title carries the loaded version; the three failure paths are dialogs, not throws: no session route, no RPC bridge, and an RPC error ("the server half did not answer").

Where the numbers change

A pass ends, the host emits session.idle, and the block re-reads that session only. A purge from either surface refreshes afterwards (the dialog passes after, the sidebar's [purge] does the same). A route change re-runs the claim's effect because props.sessionID changed. The render itself only maps spans to colours: sidebarLines decides what the block says and is pure, so the smoke test pins the block without a host.

The one link that can be missing

sidebar.tsx is imported dynamically from setup and its failure is caught, so a host without ui.slot/storage.memory, or one that cannot resolve @opentui/solid for a plugin file, still gets the dialog. The dialog's own sidebar: row reports which of the three states it is in (active, disabled, unavailable), which is the only way to tell "the block did not appear" from "the host never asked" without a log line.

One purge path, journal included

purgeWithUndo looks up both lists, removes the turn, then captures the vanished entry. The tool already did this; /context purge did not, so a later /undo could not restore it - the known gap. The dialog would have added a third unjournaled surface, so the sequence moved into one function and all three call it. The TUI handler saves through store.mutate, the same lock and cache the pass uses.

Traps

  • No default key is claimed: the id is the config key a user binds. The layer is mode: "global" so the palette finds it outside the prompt's base mode.
  • Only one dialog is active at a time. The flow is sequential (status select resolves, then the purge select opens); opening a second dialog from an actions footer would strand the first promise.
  • The RPC schema is Standard Schema v1, hand-rolled, so the plugin keeps no dependency on the host's schema library. The host validates input and output: a malformed request returns rpc.invalid_input with our own message, and a reply that drifts from StatsReply fails the call rather than reaching the dialog.
  • The host resolves the TUI entrypoint before anything else and loads it next to the server half; a first install can need a restart before the command appears. updateCheck:false still registers it, and sidebar:false only removes the block.
  • The sidebar file carries its own /** @jsxImportSource @opentui/solid */ because the installed copy ships no tsconfig.json: the pragma, not the compiler option, is what makes Bun resolve the JSX runtime for a plugin with no node_modules. The option in the repository's tsconfig is for typecheck only.
  • A click is not a dialog choice, so [resume] confirms first - a stray click must not spend a model turn. [purge] re-reads and confirms like the dialog does, and [status] opens the same dialog.
  • workingTokens includes the current turn, which is always kept, so an over-cap bar is normal mid-turn. The block paints the working line as a warning (never the whole block) and the dialog's description says why.
  • One bar is statusBarParts, split into filled and empty: a single string cannot colour half a line. statusBar stays for the dialog's plain rows.
