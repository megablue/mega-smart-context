The TUI half - a status dialog, a session panel, a sidebar block and one update toast

Status: shipped (v0.1) - Read when: tui.ts, the mega-smart-context.status palette command, the status dialog, its RPC bridge (STATUS_RPC, stats, purge, notice), src/core/status.ts, the sidebar.content block (src/tui/sidebar.tsx, src/tui/status-store.ts), the session.panel report (src/tui/panel.tsx, panelSections), the update toast, "the command does not appear", "the block does not appear", "the block shows an old number", "the panel does not open", "the server half did not answer".

What it does

The dialog

  • One palette command, Context status (id mega-smart-context.status), opens a dialog.select: a memory bar, a working-window bar, turns kept and dropped, pending/archive/ref counts, the host-system size when the last pass measured one, whether the sidebar draws and whether the panel can open, then Resume and Purge a turn….
  • It pulls: one stats RPC when the command runs, and one refresh before the purge list.

The block, the panel and the actions

  • The sidebar block appends to sidebar.content, so it is the last item inside the sidebar's scrollable list (the panel's bottom edge would be sidebar.footer), and draws the same reply as six short lines plus [status] [resume] [purge]. The two budget numbers are right-aligned to a shared width so the slashes line up, and an over-cap line carries a * before its value. The last line says how old the numbers are (measured 6m ago); it took the slot the host-system size used to occupy, because a size the glance cannot act on was less useful there than knowing whether the block is current. The title is bold, as the host's own headers are; the numbers stay plain. It renders from an ephemeral per-session store that is filled by a pull, never by the render; its click targets fire on mouse release.
  • The session panel (palette command mega-smart-context.panel) opens through ui.panel.open and appends to session.panel; it renders only for its own panel name. It is the full report: both budgets, the host-system size, the goal, a sparkline of the last passes, a measured … line once a minute has passed without a write, every pending and archived turn with [purge], the pinned notices with [retire] on the superseded ones, the undo state, and [refresh] [resume] [dialog] [close]. It reads the same mirror as the block.
  • Resume sends the plugin's cue through client.session.synthetic - the same channel as /context resume, so no user message and no new turn. The click asks first; the dialog row does not.
  • Purge lists the pending then archived turns, confirms, and deletes the chosen one through the server half. The deletion is journaled, so /undo can put it back.
  • The same entrypoint runs the once-a-day update toast, independently of the dialog and the block. updateCheck and sidebar do not gate the command.

How & why

Why a dialog before a sidebar

The dialog API needs no dependency at all, so phase 0 shipped the same numbers through the host's own dialog.select. The sidebar slots render JSX and need @opentui/solid: they are phase 1, added on top of the same reply and the same RPC.

The two halves keep separate stores

The server half owns the record in the host's KV (plugin:<id>:session/<sid>). The TUI half's storage.store is a per-key JSON file under ~/.local/state/opencode/<channel>/tui/plugin.<id>.<key>.json - the update check writes one, and it is not the KV. The dialog and the sidebar therefore cannot read the record directly. They ask the server half over the host's plugin RPC: POST /api/rpc/mega-smart-context/stats, routed to the last registered definition with that id. Every loaded instance registers identical handlers, but each instance caches its own copy of the record: one that read a session before another saved it kept answering from that older copy, and a real ODT session showed the cost - the block painted win 432k / 40k from a 07:24 snapshot while the stored record said 3,335. The stats handler therefore loads with fresh: true, which skips the cache and replaces it with what is stored. The sidebar's mirror is the third store: storage.memory("sidebar"), ephemeral, one entry per session, gone when the TUI exits.

A stale mirror, and a write that refuses

Two rules in SessionStore cover the two directions. Reads that the user sees (stats, /context) and every write pass { fresh: true }, so they start from the stored record rather than from this instance's cache; a failed read keeps the cached copy, because a storage hiccup must not forget a session. Writes are guarded: save compares the stored updatedAt with the copy it was handed and, when the stored one is newer, refuses, adopts the stored record, and logs which stamp won. The refused caller never writes its copy, so an old instance cannot roll back a newer trim or a memory edit.

mutate runs its callback once more on the newer record after a refusal - safe because the first attempt was never saved - and throws StoreConflictError if the second attempt loses too. The tool turns that into a normal failed call, the stats/purge/notice handlers into an ok:false reply, and /context into a sentence rather than a silent no-op. The guard is a timestamp comparison, not a lock: the read and the write are separate, so two saves inside the same round trip can still interleave, and two stamps in the same millisecond are indistinguishable. What it removes is the instance-lifetime window that produced the 432k block.

The sidebar is a mirror, not a meter

sidebarRefreshOf holds the pull rules: nothing for an empty id, nothing while that session's pull is in flight, nothing inside SIDEBAR_STALE_MS (15s) unless force, and nothing at all when the host has no RPC bridge. A failed pull keeps the last numbers rather than blanking the block. The store is bounded to MAX_SIDEBAR_SESSIONS (32) by dropping the oldest pull, so a TUI left open for days does not accumulate a record per session it ever showed.

Pull, never render

The command runs rpc.stats once, then builds the rows; the block's effect asks once per session and once per idle pass. A render path never calls RPC, so an idle terminal makes no requests. Choosing purge re-reads the stats first: a pass between opening the dialog and choosing the row could have archived or purged a turn, and a stale id would only fail. The status rows are disabled so Enter lands on an action; Purge is disabled when both lists are empty. The title carries the loaded version; the three failure paths are dialogs, not throws: no session route, no RPC bridge, and an RPC error ("the server half did not answer").

Where the numbers change

A pass ends, the host emits session.idle, and the block re-reads that session only. A purge from either surface refreshes afterwards (the dialog passes after, the sidebar's [purge] does the same). A route change re-runs the claim's effect because props.sessionID changed. The render itself only maps spans to colours: sidebarLines decides what the block says and is pure, so the smoke test pins the block without a host.

The panel is the report, the sidebar is the glance

The host hands every session.panel claim the name ui.panel.open was called with, so each plugin renders only when it recognises its own; the host's own plugins claim the same slot with append and a name check, and this one does the same rather than replace. The text is panelSections in core/status.ts, not JSX: budgets, goal, sparkline, pending, archive, notices and undo are all rows with optional actions, so the smoke test pins the whole report without a host. panel.tsx only maps spans to colours and actions to handlers.

Every action asks first through a dialog: [purge] and [retire] are clicks, so a stray one must not delete a turn or unpin an instruction. The retire rule lives in core/notices.ts and refuses the newest notice, which is the live instruction; the panel simply draws no [retire] on it. A purge or a retirement forces one refresh afterwards, so the panel and the block both show the new record. [refresh] forces by hand; [dialog] opens the same select; [close] calls the host's close.

The sparkline keeps the last PANEL_HISTORY_WIDTH (40) working-window samples and scales to the tallest, not to the cap: the shape is the point, and a window that never nears its cap would otherwise be a flat line. The archive lists its newest PANEL_ARCHIVE_ROWS (12) and one collapsed count for the rest. The panel is not gated by sidebar: turning the block off skips only its claim, and the mirror it shares is still made when the panel can render.

The one link that can be missing

sidebar.tsx and panel.tsx are imported dynamically from setup, separately, and each failure is caught, so a host without ui.slot/storage.memory, or one that cannot resolve @opentui/solid for a plugin file, still gets the dialog. A module is only imported when it has a chance: the sidebar when sidebar is true, the panel when ui.panel exists - a claim aimed at a missing path would otherwise append to the nearest surviving ancestor. The dialog's own sidebar: and panel: rows report which state each is in (active, disabled, unavailable), which is the only way to tell "the block did not appear" from "the host never asked" without a log line.

One purge path, journal included

purgeWithUndo looks up both lists, removes the turn, then captures the vanished entry. The tool already did this; /context purge did not, so a later /undo could not restore it - the known gap. The dialog would have added a third unjournaled surface, so the sequence moved into one function and all three call it. The TUI handler saves through store.mutate, the same lock and cache the pass uses.

Two edges, and how a line reaches them

A right edge is a layout, not a string. SidebarLine.spread says "the LAST span sits on the block's right border, everything before it stays together on the left", and sidebar.tsx draws that with a flexGrow spacer before the last span. The header puts its version there, and each budget line puts its numbers there, so the numbers end on the same column as the version whatever the sidebar width is - nothing pads to a guessed column.

The spacer is deliberately not justifyContent="space-between": a budget line has four spans (label, filled cells, empty cells, numbers) and space-between would pull the label, the filled cells and the empty cells apart as well, with the bar's fill drifting away from its own track. sidebarText has no width to stretch, so it joins the left spans with nothing and puts one space where the gap is - the same line, one space wide. The panel's header uses the same two-edge row with its tagline beside the name.

The bar is a fixed length

STATUS_BAR_WIDTH is 18 cells, about double the original ten, and it is the same number in the dialog, the block and the panel. The slack a wider pane gives lives between the bar and the numbers, which is why a longer bar could not eat it: at the observed width the label, the bar and the widest numbers (*122k / 40k) come to 35 cells, so the flexible gap keeps a few cells of slack. A narrower sidebar is one constant away from a shorter bar, and the tests measure the width through the constant rather than a literal.

One name, two halves

The name lives once as PRODUCT_NAME in core/prompts.ts, re-exported by core/status.ts so the terminal half still takes its surfaces from one module: the two drawn headers, the dialog's title, the update toast and the /context report's first line all read it, while the RPC id, the panel name, the command ids and the config filename stay lowercase because those are identifiers the host routes. It sits in prompts.ts because the dependency runs that way - status.ts imports prompts.ts, and a constant in status.ts would have to be imported back into the file that renders the report. The report is plain text, so it has one edge, the name with the build right behind it: Mega Smart Context v0.1.30 · memory ….

Traps in the host

  • No default key is claimed: the id is the config key a user binds. The layer is mode: "global" so the palette finds it outside the prompt's base mode.
  • Only one dialog is active at a time. The flow is sequential (status select resolves, then the purge select opens); opening a second dialog from an actions footer would strand the first promise.
  • The RPC schema is Standard Schema v1, hand-rolled, so the plugin keeps no dependency on the host's schema library. The host validates input and output: a malformed request returns rpc.invalid_input with our own message, and a reply that drifts from StatsReply fails the call rather than reaching the dialog.
  • The host resolves the TUI entrypoint before anything else and loads it next to the server half; a first install can need a restart before the command appears. updateCheck:false still registers both commands, and sidebar:false only skips the block's claim; the panel is independent.
  • The sidebar file carries its own /** @jsxImportSource @opentui/solid */ because the installed copy ships no tsconfig.json: the pragma, not the compiler option, is what makes Bun resolve the JSX runtime for a plugin with no node_modules. The option in the repository's tsconfig is for typecheck only.

Traps in the drawing

  • A click is not a dialog choice, so [resume] confirms first - a stray click must not spend a model turn. [purge] re-reads and confirms like the dialog does, and [status] opens the same dialog.
  • Every click target fires on onMouseUp, not onMouseDown. A dialog opened while the button is still held is already on screen when it is released, and the host reads that release as a click on the new surface, so the dialog flashes and closes. The release that opens it leaves nothing behind to dismiss it.
  • meterWidths measures both budget lines before either is drawn: the value and cap columns are padded to the wider of the two, so 18k and 124k share a right edge. The over-cap * takes the gutter rather than the end of the line, so it never shifts the digits it marks. meterNumbers is shared by the sidebar, the panel and the dialog rows.
  • workingTokens includes the current turn, which is always kept, so an over-cap bar is normal mid-turn. The block paints the working line as a warning (never the whole block) and the dialog's description says why.
  • One bar is statusBarParts, split into filled and empty: a single string cannot colour half a line. statusBar stays for the dialog's plain rows. The bar is STATUS_BAR_WIDTH (18) cells; only the bar needs the width, because the numbers ride the right edge as the line's spread span.
  • The panel claim is guarded twice: the module is imported only when ui.panel exists (an additive claim aimed at a path the host does not publish appends to the nearest surviving ancestor) and its render checks input.name (every plugin's claim sees every open panel).
  • The panel, the block and every click target are now seen in a live TUI (10/25): the palette command's panel row opened the full report, so the guarded claim does resolve on a host that publishes ui.panel, and the click targets fire. Smoke still pins panelSections/panelText, the sparkline and the retire schema; what the host draws is the one thing it cannot pin.
