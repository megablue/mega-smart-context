Mode notices - the PLAN/BUILD mode the model is told it is in

Status: shipped - Read when: the PLAN/BUILD mode, event.agent, record.mode, the mode: line in the state note, modeReminderOf, collapseModeNotices, "the model kept acting in Plan mode", or any change to the context pass that touches the transcript, the notices or the tail note.

This page exists because the same bug shipped three times: the stale Plan reminder outliving the Build switch (62ca41e), then nothing being pinned at all after the host changed the shape (146 passes, 11/27), then a text-shape fix that installed cleanly and never fired because the instruction is not in the transcript. Read the traps before touching anything in the pass.

What it does

  • Records the live mode on the session record as record.mode ("plan" or "build"), from the request's agent, on every pass.
  • Renders it as one line in the trailing <smart-context-state> note: mode: plan - do not modify files; tell the user to switch agents or mode: build - edit and run commands.
  • Keeps only the live mode. A later switch replaces it; an agent that is neither Plan nor Build clears it.
  • Pins host text notices separately, in one system part, and excludes the mode from that part so a switch never moves the system prefix.
  • Still retires a superseded Plan/Build text reminder when the fallback path pinned both, so a stale imperative cannot read as the live instruction.

How & why

The authority ladder

  1. event.agent - the request names the agent it runs on. Reduce it with agentNameOf (a string, or an object with name, id or agent), then modeOfAgent: exact "plan" or "build", anything else clears record.mode. This is the authority because it arrives on every request and cannot be evicted.
  2. ctx.session.get({sessionID}).agent - only when the event names no agent. The session row carries the same value (session_v2.agent). It costs a host round-trip per pass, which is why it is not the first choice.
  3. The instruction text - the fallback for a host that names no agent at all. See the shapes below.
  4. Nothing - no mode line; never guess.

Why the transcript cannot be the authority

On 2026-11-27 session ses_de657349dffeT8H5apLdq4zzhv ran 146 passes with an empty record.notices while the mode switch sat in session_message at seq 280, as a type: "system" row with metadata.notice: "instructions" and instructionSources: ["core/agent"]. The transform never received it: event.messages carries the conversation, not that row. The user had to type "you are in build mode" at seq 1274. A first fix that taught the classifier the new text shapes (210e50c) installed cleanly, passed the smoke, and still showed noticeTokens: 0 - proof that no text matcher can fix this. The mode lived on the session all along: session_v2.agent = "build", plus an agent-switched row {"agent":"build","previous":"plan"}.

The smoke cannot see this: it feeds buildPayload directly, so it proves the render and not the host channel. Every claim about "where the notice arrives" has to be checked against the real database or a live pass.

The text shapes (fallback only)

hostMessageOf classifies a host-injected message that is not from the plugin (no megasc_ id, exactly one text part, a trailing @n@ stripped). A mode instruction has been seen in three shapes, and modeReminderOf accepts all three:

  • a user message whose whole text is <system-reminder>...</system-reminder>, matched by substring inside the block (the original shape);
  • a user message whose whole text is <system-update>...</system-update>, unwrapped before classification (what the host repaints the instruction into);
  • a system-role message whose text opens with the full sentence: You are in Plan mode. or You are no longer the Plan agent, so you are NO LONGER in Plan mode. .

The full lead sentence matters: a bare "You are in Plan mode." stays a real turn, so a human asking about the mode is never pinned as an instruction. A message that merely quotes a tag, or adds prose after it, also stays a turn.

Where it renders

  1. system: ...hostSystem, POLICY, APPEND_NOTE, project facts, then the pinned non-mode notices under ## Pinned host notices.
  2. messages: the memory block (megasc_memory), the working window, the current turn, and last the <smart-context-state> note that carries mode:.

The split is deliberate. The state note is the only part allowed to churn, and it sits after the current turn so a live number cannot invalidate the turn inside a tool loop. The system part must stay still: a Plan/Build switch that rewrote it would cost a prefix-cache miss on every request.

Only the live mode

Plan and Build contradict each other; pinning both leaves the old "do not implement, tell the user to switch agents" reading as the instruction (that was 62ca41e). collapseModeNotices keeps the mode the host emitted last and retires the other into record.retired; re-emitting the retired mode brings it back and retires the other in turn. The agent path is simpler still: one field, overwritten every pass, deleted when the agent is neither mode.

What compaction does not touch

record.mode and record.notices are top-level record fields. checkpointAppend moves base and updates only; a host checkpoint archives the turns it replaces and never clears the mode or the notices. The tail note is rebuilt from the record on the next pass, so the mode reads correctly before and after any fold. If a future change moves the mode into the memory document, this stops being true - do not.

Traps

  • Do not infer the mode from the transcript alone. The host has already shown it can keep the instruction out of event.messages entirely.
  • Do not require a shape. The host has used three; a matcher that knows one is how the 146-pass session happened.
  • Do not render the mode in the system part. It belongs in the tail note, or every switch pays a cache miss.
  • Do not keep the superseded mode. One mode, retired or overwritten.
  • Do not treat a sentence as an instruction. The full lead is the gate; a human question must stay a turn.
  • Do not assume every hook has an agent. The host docs say the title hook has neither agent nor tools; context, compaction and generate do.
  • Do not generalise an agent name. Exact plan/build only; a custom agent clears the mode rather than inheriting one.
  • Do not trust the smoke for a host channel. It proves the render; the database and a live pass prove the arrival.

Config keys / UI

  • No config key. The mode is derived, never set by the user or the model.
  • The only user-visible surface is the mode: line in the state note.
  • smart_context { action:"notice" } lists pinned text notices and retires a superseded one; the newest is refused. The mode itself is not a notice the model may retire.
