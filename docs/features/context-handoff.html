Context handoff - the request the model actually sees

Status: shipped (v0.1) - Read when: the request payload, the memory block, the working window, buildPayload, selectWorkingWindow, turn boundaries, or "the model lost the conversation".

What it does

  • Replaces event.messages on every request with the memory block, the newest turns that fit the working budget, and the current turn.
  • Pushes the standing policy into event.system once, deduped by exact text.
  • Never edits the durable transcript; every pass is re-derived from the raw transcript and the session record.
  • Keeps the current turn intact, including every tool call and result the model just asked for.
  • Reports the estimated memory/working usage in the block's first line.

The user-visible contract is in docs/SPEC.md under "What the model sees" and "Budgets".

How & why

Turns and the window

A turn starts at a real user message (isRealUser: role user, not a megasc_ injected id) and ends before the next one. The turn id is the user message id, because indices move when the host compacts and ids do not.

selectWorkingWindow walks backward from the newest turn, accumulating span.chars. It stops when the next whole turn would exceed workingTokens * charsPerToken. The current turn is always kept, even when it alone exceeds the budget; overBudget is reported instead of dropping the results the model just requested. A cut at a turn start cannot split a call from its result; balanceCuts is the assertion, and the window still checks it as a guard for a host that starts mid-turn.

What leaves, and when

record.seenTurns is the window from the previous pass. On a new user turn, a turn in seenTurns that is not in the new window becomes a PendingTurn with a mechanical gist and its eroded raw messages. The first pass only seeds seenTurns: enabling the plugin mid-session is not an eviction of turns it never managed.

Pending turns age by new user turns, not by requests: the age step runs only when the window's turn id list changes. A ten-call turn must not consume ten eviction leads. With autoArchive, a pending turn older than evictionLead is archived; with it off, it is dropped when the lead expires. See archive.md.

Erosion and reasoning

erodeToolResults shortens one result over maxResultChars, keeping a head, a tail and a marker with the missing count. The call and result keep their ids and order. Reasoning is not touched: it is passed through exactly as the host sent it. Dropping it from a completed turn would change bytes the model has already been sent, which is the one thing that cools a provider prefix cache, so the old "keep it only for the current turn" rule was removed.

Because the pass re-erodes everything in the window, a tool result cannot budget its own way out of it: expand pages at min(expandDigestChars, maxResultChars) including its footer, so a page is never cut again. That is also why the delegated-reply note names maxResultChars: it is the durable capacity of a subagent's answer, not its own context window.

A result's shape is part of the contract. The host hands a tool result as one of three shapes and each survives erosion: text (value is a string), content (value is an array of parts) and json (value is structured). content is the trap: OpenCode's SessionModelRequest.prepare maps over that array (l.value.map), so writing a string into it aborts the request and the TUI shows "session failed". Only the text parts shrink; the array and its non-text parts stay. json is left alone because there is no text to cut without retyping the result. This bites only a multi-part result that is also over maxResultChars; a single-text result is typed text and never takes that path. Pinned by: "a content result keeps its array shape", "the durable content result was not mutated" and "a structured result keeps its value".

The block and the policy

The memory message is { id: "megasc_memory", role: "user", content: [text] } and is prepended to the window. Values in it are JSON-quoted so a newline in a note cannot change the shape. The policy is a static system part. The block carries no live counters: a budget: line would be rewritten on every pass, so every byte after it would miss a provider prefix cache. The numbers are read on demand from action:"stats" and /context, and read with no key returns the pure document.

No timestamp or pass counter is rendered. Two passes over the same transcript and record must produce the same bytes, and the smoke asserts it.

Prefix stability

The outbound prefix is [host system parts][POLICY][pinned notices][memory block][verbatim window]. Everything before the window is stable by construction; the window is where a mistake would cost a cache. So no rewrite may depend on a newer turn. erodeToolResults is a pure function of the message's own bytes; reasoning is passed through untouched; selectWorkingWindow cuts only at a turn boundary. A message that has been sent therefore looks the same on every later pass. The pinned-notices part stays last in system and is never reordered, so a mode switch only ever appends one part at the end of the stable prefix rather than moving an earlier one. The two open cracks are the ones that are not per-message: the memory block's ## Pending eviction section changes on a new turn that evicts one, and a new memory write changes the block.

The record keeps a pass history

Alongside lastReport (a single snapshot for /context), each pass appends one PassSample to record.history: the enabled page beside the disabled baseline, both exact at that moment. history is not part of the payload, so it does not affect the bytes two passes produce. It is trimmed to MAX_HISTORY (200), keeping the first sample and the newest; it is optional, so a record written before the feature loads unchanged. analyze.md reads it.

/context arrives as a real turn

The host's command executor has no display-only channel: ctx.command.transform hands execute the session and the prompt, and the documented answer path is ctx.session.prompt. That is what the adapter does, so a /context report is a genuine user turn - visible in the TUI, counted in the working window, archivable later like any other turn. ctx.session.synthetic is not a display-only escape hatch either: it marks the message synthetic and skips prompt hooks, but it still admits an inbox item and starts a model turn (verified live). That is exactly why the report uses prompt and /context resume uses synthetic with resume: true: a report is an answer, while resume exists to start a turn, and its sentence is classified as a cue so the new model turn adds no working turn and ages no pending eviction. prompt stays for the report: it is short and it does not corrupt memory. If it ever crowds the window, shorten the report rather than looking for another channel.

Host messages that are not turns

Four kinds of message reach the model as a user message that no one typed, and hostMessageOf is the single classifier for all of them (role user, not a megasc_ id, exactly one text part, a trailing @n@ stripped): a Plan/Build mode reminder, the output-token-limit nudge, a background job's completion (a <shell> or <subagent> block), and a resume cue. The first two are notices, the third is a job and the last is a cue. A message that merely quotes a tag, adds prose after it, or uses more than one part stays a real turn. So does a reworded interruption: each cue is matched whole against its one sentence, so a variant falls back to the old behaviour rather than being guessed at.

A job is not a boundary. isRealUser excludes it, so it annexes to the newest span: its bytes stay in the window and count toward that turn's budget, and it ages no pending eviction, because the work it reports is work the model already asked for. It is not pulled out, because the result answers a call the model is waiting on. Live rows confirm the shapes: a shell or subagent row arrives as one text part wrapped in the tag, and the nudge is a plain sentence with no metadata.

The nudge is a notice, so it rides the rail: stripped from the window and pinned beside the mode reminders, listed by action:"notice", and protected by the same newest-refusal. Pinned by: "the output-limit nudge is a notice", "a shell completion is a job", "a job does not start a turn", "a job completion annexes to the turn that started it", "a job completion does not age a pending turn", "the interrupted-response continuation is a cue", "a cue is never pinned on the notice rail", "a cue does not start a turn", "a resume cue annexes to the turn it continues" and "a resume cue does not age a pending turn".

The resume cue

A cue is the same kind of tail, but it reports no result. isHostTail (job or cue) is what isRealUser excludes, so the sentence stays in the window, counts toward the turn it continues, and ages no pending eviction. There are two cue sentences: the host's "The previous response was interrupted..." (all 23 live rows byte-identical) and the plugin's own RESUMED_TEXT, which /context resume admits through ctx.session.synthetic with resume: true. The plugin's sentence carries a [mega-smart-context] marker so an accidental human copy is unlikely, and the same sentence without the marker stays a real turn; it deliberately does not carry a megasc_ id, because context.ts filters injected ids out of the window before the cue could ever reach the model. It is not pinned: a notice is a standing instruction replayed on every pass, while "continue from where you left off" is stale the moment the model has continued, and pinning it would also hand the newest-refusal rail to a nudge so the live mode notice could be retired. Without the classifier it would be a phantom turn, exactly like a mode reminder.

The host's own system prompt

The flip side of the turn count is what the plugin never counts: the host's own instruction set rides in event.system. buildPayload measures the parts it did not write (hostSystemTokens, hostSystemParts) and /context prints host system ~X est (N parts) - display only, in no budget, absent when the host supplies none. With debug on, the pass logs the count and the head of each part, which is the check that event.system really carries the blobs.

Host notices are pinned, not replayed

The host admits a Plan/Build switch as a synthetic user message whose whole text is a <system-reminder> block (and the output-limit nudge the same way), not as a system part. Counted as a turn it does two bad things: it inflates workingTurns, and it changes the window's turn-id list, which ages a pending turn on a mode switch the model never made. splitNotices removes such a message from the conversation and buildPayload runs turnSpans over the rest. A message that merely quotes the tag, or adds prose after it, stays a real turn.

Every distinct notice text is folded into record.notices by upsertNotices and rendered by renderNotices into one system part appended after POLICY, newest first, headed ## Pinned host notices. Dedupe is by exact text and at never moves, so a re-run is byte-identical; the stored id does move - to the newest occurrence in the transcript - and the list is kept in recency order, so a text the host re-emits moves to the end. First-sight order freezes instead, and the rail ends up refusing the stale text while allowing the live one; observed live with the two real mode notices. A stale block the host still carries is dropped before the fresh one is appended. The list is capped at MAX_NOTICES (8, oldest dropped) and each text is head-kept at 4000 chars.

The model retires a superseded notice with action:"notice" remove:"<id>", which writes record.retired (bounded by MAX_RETIRED, 32). The newest is the live instruction and a removal of it is refused. Pinned by: "a mode switch is not a turn", "a mode switch does not age a pending turn", "the record pins each distinct notice once", "a re-seen notice moves to the end" and "the newest notice refuses removal".

Why a removal has to write a retirement

The context pass re-runs splitNotices on every request, so a notice that is merely deleted from the record comes straight back - the text is still in the host's window. upsertNotices therefore skips a found text whose newest occurrence id is retired, which is why the stored id tracks the last occurrence in the transcript rather than the first: that is what separates a stale copy still in the window from a genuinely new emission. The same text under a new id clears the retirement and returns, because a re-emitted instruction is live again. Retirements are bounded by MAX_RETIRED (32) and need no other cleanup. Pinned by: "a retired notice is not re-added while its text is still in the window", "the same text emitted under a new id returns", "the retirement clears once the text is re-emitted" and "the retirement list is bounded".
