Feature refs - a pointer plus a gist

Status: shipped (v0.1) - Read when: the ref action, pageCandidates, extractSection, extractHtmlSection, refVerdict, docs/features, or "should I paste the section or point at it".

What it does

  • Stores a feature-map pointer (page#section) plus the model's one-line gist in memory.refs.
  • Reads the real section from docs/features/<page> - the HTML page first, the Markdown page as a fallback - and reports the gist and section token costs.
  • Tells the model which representation is shorter; the model decides.
  • Counts the reference against memoryTokens; a reference to an unreadable section is still stored, with a warning.

The user-visible behavior is in docs/SPEC.md under "Feature-map references".

How & why

The page argument

pageCandidates strips a leading docs/features/, normalizes separators, and rejects an empty path or one containing ... It returns the files to try, in order:

Page argumentCandidates
refs (bare)refs.html, refs.md
refs.mdrefs.md, refs.html
refs.htmlrefs.html, refs.md
notes.txtnotes.txt

createFsFeatureMap resolves each candidate under <root>/docs/features/, checks the resolved path is still inside that directory, and returns the first one that both exists and holds the section. A bad page is undefined, not an exception.

The two formats

docs/features/ may hold a generated index.html and one *.html per page, with Markdown sources that a converted map has dropped. A bare page name therefore prefers the HTML page; an explicit extension keeps the named file first and the sibling second, so refs.md still resolves after the .md source is gone.

htmlToText flattens an HTML page back into Markdown-shaped text - <hN> becomes # x N plus the heading, <li> a bullet, block boundaries newlines, entities decoded - so extractSection runs unchanged over either format. This is an approximation of what the model reads, and it is deliberate: markup the model never sees is not counted as section text. On this repository the HTML section costs ~97% of its Markdown twin.

The section argument

extractSection matches a heading exactly first, then by case-insensitive substring, so how-why finds ## How & why. The returned text includes the heading and stops at the next heading of the same or a higher level, so a ## section does not swallow its ### subsections' siblings. A missing page or section returns undefined; it never returns an empty string, which would read as a real zero-cost section.

The comparison

refVerdict(gist, sectionText, charsPerToken) reports:

  • gistTokens - the model's one-liner;
  • sectionTokens - the section it points at;
  • useRef - sectionTokens > gistTokens;
  • saving - the difference.

The tool's reply says either "the reference is shorter (saves ~N)" or "the gist is longer than the section; inline the section instead". This is the mechanical half of "whichever takes fewer words"; the model still chooses.

Storage and the cap

A ref is { page, section, gist, tokens: gistTokens }. Re-adding the same page#section replaces the entry instead of duplicating it. The write goes through the same memoryTokens check as a patch: if the new ref would push memory over the cap, the previous refs array is restored and nothing is written. The pointer is stored even when the section cannot be read; the reply says so, because a pointer that cannot be expanded is still a note to the model.

Tests that pin it

  • "a feature-map ref is stored" and "a ref to a real page resolves against the map" - the adapter path.
  • "a bare page name prefers the HTML page", "an explicit extension keeps the named file first", "a page path cannot escape docs/features", "an empty page has no candidates", "an unknown extension is left alone" - pageCandidates.
  • "an HTML entity decodes inside a heading", "an HTML list item becomes a Markdown bullet", "an HTML section keeps its ### subsections", "an HTML section stops at the next same-level heading", "a missing HTML section is undefined" - htmlToText and extractHtmlSection.
  • "Markdown section extraction is unchanged" - extractSection.

The smoke uses context-handoff.md / How & why, which resolves against this repository in either format; the missing-section branch is exercised by the adapter's undefined return.
