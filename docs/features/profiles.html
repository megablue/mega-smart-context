Profiles - one bundle of per-session settings

Status: shipped (v0.1.40) - Read when: a profile or a model mapping, defaultProfile, "switch the budget for this session", "the caps moved with the model", or the sidebar's [profile] target.

What it does

  • Names a partial config - a profile - in the same user config file, and applies it to one session's budget: memory, working window, erosion, archive bounds, refs and charsPerToken.
  • Chooses it three ways: a manual pin from the sidebar or /context profile, a modelProfiles mapping for the model in use, or defaultProfile when nothing else matches.
  • Keeps a manual pin until the user picks auto: changing the model never clears it, and neither does a restart.
  • Makes the switch real: the effective config decides the window, the erosion, the memory cap and the archive bounds of the next pass - not just what the dialog prints.
  • Shows the choice everywhere: a profile line in the sidebar block, a row in the status dialog and the panel, a line in /context, and the profile RPC method.

docs/SPEC.md owns the user-visible behavior; this page owns the mechanism.

How & why

What a profile may set

A profile is a partial config limited to SESSION_KEYS: memoryTokens, workingTokens, charsPerToken, evictionLead, autoArchive, archiveMaxTurns, archiveMaxChars, parentArchive, expandDigestChars, refs, maxResultChars. The process and install keys - enabled, subagents, manualCommand, updateCheck, sidebar, debug - are refused, with the same strictness as an unknown top-level key. A model picking a profile must not be able to decide whether the sidebar exists.

Validation reuses coerceValue, so a profile's numbers go through the identical clamps as the top level (memoryTokens floor 1000, workingTokens floor 500, charsPerToken 2-8, archiveMaxChars floor 10000, maxResultChars floor 200). Profile names are letters, digits, dot, dash or underscore; they end up in dialog rows and JSON keys.

The selection order

Exactly four steps, first match wins, in chooseProfile:

  1. a manual pin on the record - { mode: "profile", name } or { mode: "base" };
  2. a modelProfiles entry for the request's model;
  3. defaultProfile;
  4. the base config.

The pin is checked before the model on purpose: a manual switch is the user speaking, and a mapping is only a default. A pin has no expiry - record.profile is cleared only by picking auto - so switching models, restarting, or letting the session idle cannot undo it.

Model keys are tried most specific first: provider/model#variant, then provider/model, then a bare model (modelKeys also accepts model#variant). That lets a variant pin a different budget from the same model without one.

Where the effective config is derived

The pass stamps record.lastModel from event.model, then resolves the choice and merges the profile's keys over the base for that pass only. The record never stores the effective config - it stores the two inputs (pin and model stamp) that reproduce the same answer, which is why a config edit or a downgrade cannot leave a half-applied budget behind.

Every other surface re-derives through configForRecord(config, record): the tool (one cached load at the top of runMemoryTool), /context, budgetOf/renderStats, statsOf and the panel. A pass that names no model leaves the previous stamp alone, so one odd request cannot silently flip an automatic session back to the default.

A pin that names a profile the config no longer defines is not an error at load (the record is data, not config): the session runs the base and every surface says base · <name> is not configured until the user picks a profile or auto.

The surfaces and the write path

The sidebar draws profile <name> · auto|pinned|default directly under the header and adds a [profile] target to the action row; the target opens a dialog.select whose rows are auto, base and every named profile with its overrides (profileSummary). The panel's Budget section shows the profile, the model and, for a pin, "pinned until you pick auto". /context profile prints the inventory; /context profile auto|base|<name> writes it without a TUI.

All three write paths - the dialog, /context and the RPC - go through the store's lock and the same conflict handling as purge and notice, and all reply "applies from the next pass": the request already in flight was measured against the old caps. The RPC re-checks the name against the loaded config, so a picker row whose profile was just deleted is refused rather than pinned.
