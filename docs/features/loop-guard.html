Loop guard - one redirect for a turn that repeats failed work

Status: shipped (0.2.0) - Read when: a turn repeats the same failing call, a process check line appears in the trailing state note, loopGuard / loopGuardMode / loopGuardMinCalls / loopGuardEnvelope, the envelope learning, record.guard, or "the guard fired twice".

What it does

  • Folds the newest prompt-turn's completed tool calls into a compact digest: tool name, normalized argument fingerprint, success/failure, error signature, edit and verification counts, new-file and read activity.
  • Returns at most one short process check redirect per turn when the turn repeats a failed call and error three times, has five failures with no verification after eight calls, makes eight edits since the last test/build/typecheck, or runs past its envelope with the same failure still repeating.
  • Appends that line inside the existing trailing <smart-context-state> note. Every earlier payload byte stays identical, and the current turn is never rewritten.
  • Never redirects a turn whose latest verification succeeded after its latest edit. A new user turn resets every per-turn counter; a completed older turn is never re-judged.
  • Makes no model call, aborts nothing and mutates no tool result. The redirect mirrors the agent's own actions back at it and tells it to change the hypothesis or the input.

This page is the mechanism. The guard's place in the request layout is in context-handoff.html; the user-visible contract belongs in docs/SPEC.md.

How & why

The unit is one prompt-turn

updateLoopGuard(state, messages, options) finds the newest real user message with isRealUser from view.ts and folds only that slice. A job completion or a resume cue is not a turn start, so it cannot reset the guard or hide the turn that is looping. Older completed turns are never looked at: a fresh pass over a transcript whose last turn is new reports the new turn, even when the previous turn repeated a failure ten times.

The digest is a cursor, not a replay

state.calls is the number of completed call/result pairs already folded. On every pass the guard pairs the current turn's calls with their results and folds only [state.calls, length), so a turn that grows one tool call per request costs one fold, not a re-scan. Two passes over the same messages fold nothing new and return the same decision. If the host trimmed the current turn and state.calls is now larger than the completed pairs, the counters restart from the raw transcript while the delivered redirect is kept: one redirect per turn is the invariant, not one per fold.

What counts as a repeat

A call's key is its canonical tool name, a stable FNV fingerprint of its arguments and the normalized error signature. The fingerprint sorts object keys and bounds depth and string length, so key order or a changed number in a message does not create a new call. The signature is the first line that matches ERROR_SIGNAL, with ANSI codes, hex addresses, paths and numbers removed, so the same failure at a different line or path still matches. Three calls with the same key is the repeat rule; three different calls that happen to fail with the same error is not. Content tools (read, view, grep, glob) only fail when the result itself says so: a test file full of assert is not a failing call.

The other three rules

  • Failures without verification. Eight or more completed calls, five or more failures, and no verification call in the turn. This catches a turn that keeps trying variations and never runs the project's checks.
  • Edits without a check. Eight edits since the last verification. The count is edits - editsAtVerify, so a successful check early in the turn does not license unlimited edits afterwards; a later check resets the count. An edit includes the edit/write tools and a shell command that changes a source file: sed -i, perl -pi, patch/git apply, or a tee/redirection into a source extension.
  • Over the envelope. The completed calls reach max(minCalls, envelope), at least one failure has repeated and the turn is not green. This is the long-grind rule. An envelope supplied by the caller wins; otherwise the p90 of this session's green-turn lengths is used once there are at least LOOP_GUARD_MIN_SAMPLES (5); otherwise the mode's fallback is 20 calls (14 aggressive). Every envelope is clamped to 4..200.

Green suppresses, and one line is stored

loopGuardGreen is true when a verification succeeded, no edit happened after it and its call index is at least the last edit's. A green turn is never redirected, even if it repeated a failure before recovering. The first non-green match stores redirectText on the state; every later pass of that turn re-renders the same text rather than rebuilding it from counters that have moved, so the redirect does not drift and the tail stays deterministic. The line names the repeated call and signature, says the turn is at N calls against the envelope, and asks for a different hypothesis or input. It never says stop.

The payload seam

The tail note is the only message allowed to churn and is already last. withGuardLine inserts the redirect before </smart-context-state>; it does not touch the memory block, the working turns or the current turn. The smoke test builds the same conversation with the guard off and on and asserts that event.system and every message before the last are byte-identical, then masks the live pool line in the two notes and asserts the only remaining difference is the redirect. A provider prefix cache therefore sees the same prefix, and a retry over the same conversation produces the same bytes.

State, bounds and the disabled switch

The state is counters plus two maps (errorSigs, repeatKeys), each capped at 64 entries by dropping the oldest; at most 32 green-turn samples; a 200-character turn id; 120-character signatures; 80-character labels; and a 600-character stored redirect. normalizeLoopGuard clamps every count, rejects non-object state and drops an unknown redirect reason, so a record written by an older build or a corrupt store cannot make the guard fire on nonsense. With loopGuard:false the pass neither folds nor renders; re-enabling it folds the current turn from the raw transcript. The guard is install-level on purpose: a profile changes budgets, not process policy.

What is deliberately absent

No paid judge, no Python dispatcher, no abort/stop verdict, and no tool-result rewrite. The upstream TokenEconomizer revision (1bfeccd) used a judge behind a gate and an abort on a second stuck segment; this port keeps the free heuristic and turns the delivery into advice in the trailing note.

loopGuardEnvelopetruebooleanSet false to keep the three fixed triggers and disable the over-length rule.

There is no TUI control and no command: the guard is a process policy, and its one visible effect is the process check line in the state note. ContextDeps.loopGuardEnvelope is the read-only seam a future project-facts layer can use to supply a learned envelope without adding a config key.
