Memory tool - the model's only write path

Status: shipped (v0.1) - Read when: smart_context, applyPatch, the memory schema, a patch that did not land, an over-cap write, or "why did the model lose a fact".

What it does

  • Exposes one tool, smart_context, with nine actions: read, patch, stats, ref, archive, purge, recall, expand, notice.
  • Merges a model patch under runtime-owned rules; the model cannot invent a key or corrupt one it did not mention.
  • Rejects a write that would exceed memoryTokens and reports the projected usage; it never trims.
  • Refuses recall without lost:true.
  • Lets a delegate read its spawning session's archive with from:"parent" on recall/expand only; every writing action stays on this session.
  • Runs every write through store.mutate, so a tool call and a context pass cannot lose each other's update.

The user-visible actions are in docs/SPEC.md under "The model surface".

How & why

The schema

Eight keys: goal (string), plan (list of {step, status, text}), facts, files, decisions (maps), open (list of strings), refs (list of {page, section, gist, tokens}), notes (string). Every key always exists; absence is an empty value, so the renderer never branches on a missing key.

Two rules decide the shape. A key whose entries accumulate is a map, so a patch that mentions one entry does not erase the others. A key that is the current state is a list, because the newest full list is the truth.

The merge

  • null at the top level resets a key to its empty value.
  • null inside a map deletes that one entry.
  • An unknown key is dropped and named in the ack.
  • Maps merge key by key; lists replace wholesale.
  • An invalid entry (a non-string map value, a plan item with no text, a ref with no page) is reported and the previous value is kept; one bad entry does not discard the rest of the patch.

The base is never mutated: applyPatch clones before it merges.

The cap

The check is estimateTokens(memoryChars(next), charsPerToken) > memoryTokens. On failure the tool returns the projected usage and writes nothing. This is deliberate: a silent trim loses content the model believes it stored, and the model is the only one who knows what matters. The model is told to compact and retry.

The envelope

The tool is registered with options.codemode: false and injected into event.tools; measured against this host, a tool without codemode:false is reachable only through execute, not by name. It returns { content: [{ type: "text", text }] } and declares no output, because a result that declares output without an output schema loses the call.

A write returns an acknowledgement to the model and nothing else; a bookkeeping call never generates a user-facing reply.

The notice rail

action:"notice" lists the pinned host notices - a mode reminder or the output-token-limit nudge - newest first; remove:"<id>" retires a superseded one. The list is written by the context pass (upsertNotices), so this is the only path that removes an entry. The newest notice is the live instruction and a removal of it is refused: a newer notice, not the model, resolves a contradiction the host injected.

"Newest" is recency of emission, not first sight. The host emits the same two texts all session and a window holds every past row, so a list that appended on first sight would freeze its order and the rail would protect whichever text the transcript happened to contain last - observed live as the stale build text protected and the live plan text removable. Re-seeing a text moves it to the end instead, so the last entry is the text the host emitted most recently; a re-run over the same transcript lands on the same order.

A removal must also survive the next pass: splitNotices re-runs every request and would re-add any text not already pinned. So notice records the retired entry (id and text) in record.retired, and upsertNotices skips a found text whose newest occurrence id is retired. The stored id moves to the newest occurrence in the transcript on each pass, which is what distinguishes a stale copy still in the window from a genuinely new emission: the same text under a new id clears the retirement and returns. Retirements are bounded by MAX_RETIRED (32) and clear themselves as the host re-emits. See context-handoff.md for where the notices are pinned.

Delegation is one field on two actions

The only cross-session read is from:"parent" on recall and expand. MUTATING_ACTIONS names every action that writes, and any of them carrying from is refused before the tool looks at the parent at all, so the field cannot become a write path. targetRecord is the single resolver - the caller's own record when from is absent, otherwise the spawning session's, resolved through parentOf. A delegated read also ends with the reply budget (delegatingNote): the caller's next pass erodes the child's answer to maxResultChars, so the child is told that ceiling before it writes. See archive.md for the four refusals and the paging footer.

Concurrency

patch, ref, archive, purge and notice use store.mutate(sessionID, fn), which serializes load-modify-save per session. read, stats, recall and expand use load and do not write.
