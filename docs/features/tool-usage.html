Tool usage - the read-only evidence report

Status: implemented (0.2 line) - Read when: tool-usage.ts, tool-calls.ts, ProjectToolUsage, toolsFolded, unusedPrompts, the tool-usage section of /context or the status dialog, "a tool was counted twice", "which tool is never used".

What it does

  • Counts completed tool calls per project: calls, successes, failures, the prompt-turns that called each tool, and the distinct sessions.
  • Tracks how long a recorded tool has gone uncalled (unusedPrompts) and which offered tools have never completed a call.
  • Renders a bounded report with the evidence needed to remove a tool. It is report-only: no tool is hidden, denied or removed, because changing the tool schema mid-session invalidates the provider cache and can break Code Mode.
  • Stores tool names and counters only. Arguments, output, paths, commands and user text never enter the project record.
  • The modules are wired into the pass, /context tools and the status sidebar. Reads are fresh and report-only.

How & why

Pairing

pairToolCalls walks messages once, remembers each call by id, and emits a pair when the result arrives. A call with no result is ignored (the turn is unfinished or the host dropped it), a duplicate result is ignored (the first consumed the call), and an orphan result is ignored. order is the result order, not the call order. isFailedToolResult is explicit: isError/error, result.type === "error", success === false, a non-zero exitCode/exit_code/code, or status of error/failed/failure. A result with no status is a success.

Turn boundary and cursor

foldToolUsage uses turnSpans: every real user message opens a turn. All but the newest user turn are complete; the current turn is never folded. The cursor is session.toolsFolded = { turn, at }, the newest completed turn already counted. With no cursor the first fold backfills the newest TOOL_USAGE_BACKFILL = 20 completed turns. A cursor whose turn is absent from the transcript is lost: the fold re-anchors on the newest completed turn and counts nothing, so a trimmed transcript cannot replay old history.

Idempotency

Each completed turn gets a usage key sessionMark(sessionID) + "|" + turn.id. applyToolUsage skips a key already in envelope.usageSeen, so a retried request, a second plugin instance, or a project write followed by a failed cursor write cannot count the same turn twice. sessionMark is the first 16 hex characters of SHA-256; the full session id never enters the project record, and the marks saturate at TOOL_SESSIONS_MAX = 12.

Counts

For each completed pair: calls and ok/failed. Each called tool gains prompts += 1 once per turn even when it was called several times, and its unusedPrompts resets to 0. Every existing row the turn did not call gains one unused prompt. The turn always increments envelope.promptTurns and, once per session, envelope.sessionsSeen. A called row gets lastAt = fold now and the session mark. (other) is excluded from the unused sweep because it is an aggregate, not a tool.

Write order and conflicts

FoldToolUsageOptions is { store, key, sessionID, now?, warn? }: store is a ProjectStore and key is its ProjectKey, so one store.mutate(key, ...) writes every selected turn while the project lock is held. sessionID is separate because a ProjectKey cannot identify a session, and the usage key needs the session hash. The project store is written first; the session cursor is set only after it succeeds. The cursor is written in place on the session record the caller already holds, because a context pass loads and saves that record under its own lock; a second SessionStore.mutate here would deadlock or race the caller's save. A project conflict (or any project-store error) is warned, leaves the cursor unchanged, and returns false, so the next pass retries; the usage keys make the retry a no-op for turns that did land.

Integration

Implemented in src/core/context.ts after foldProjectFacts: when deps.project is defined, foldToolUsage(record, raw, { ...deps.project, sessionID: input.sessionID }) folds completed turns before the session save. SessionRecord.toolsFolded/offeredTools are normalized in state.ts. The adapter passes Object.keys(event.tools) (minus the plugin's own smart_context) before the payload is built; noteOfferedTools stores the bounded list. /context tools [all] loads the project fresh and renders toolUsageReport; the status RPC attaches toolSummaryOf to StatsReply and the sidebar draws one line.

Report threshold

The header is tool usage · root · N prompts · S sessions · measured age. Used rows are sorted by lastAt descending, then name; 10 are shown, or up to TOOL_USAGE_MAX = 64 with all, with a footer naming the hidden count and /context tools all. A recorded tool is "unused" at 10 unused prompts or 5 distinct sessions; a tool in HIGH_RISK_TOOLS needs twice that (20 or 10). "Never used" is the offered list minus the recorded names. Empty states are explicit: no tool calls recorded yet, no unused tools, every offered tool has been used. toolSummaryOf returns used, offered, prompts, sessions, and unused only when something was offered.

Privacy

The pair type has no input or result field. applyToolUsage writes only normalized tool names, counters, the fold time and a short session mark. A shell command, a path, a result body or a user message cannot reach the project record, and the test serializes both records to prove it.

Tests that pin it

  • Pairing and failure: a completed call is paired with its result in result order, a call without a result is ignored, and a duplicate result is ignored, failure detection reads explicit errors, result type, success and exit fields.
  • Turn and cursor: the newest user turn is current and never folded, one user turn means no completed turn and folds nothing, the first fold backfills only the newest 20 completed turns, a second fold is a no-op and a lost session cursor re-anchors without replay.
  • Counts: usageSeen makes replayed turns a no-op even when the cursor is behind, ok and failed counts are per completed pair, prompts count once per tool per turn, however many calls it made, unusedPrompts increments for an existing tool that was not called and resets when called, sessions and sessionMarks saturate at TOOL_SESSIONS_MAX.
  • Write order and bounds: a project conflict leaves the session cursor unchanged, the project write runs before the session cursor is set, a real ProjectStore accepts the fold and normalizes it on load, the fold writes through the project key it was given, the normalizer folds the overflow into (other).
  • Privacy and report: nothing but a tool name and its counters reaches the project or session record, the report shows the header, ten used rows, and the all footer, an empty record says so, and an offered-but-never-called tool is named, the report marks stale rows and counts a used offered tool as used, unused tools need ten prompts, and a high-risk tool needs twenty, no unused tools is its own line once something has been called, toolSummaryOf counts used, offered and never-used, offered tool names are normalized, deduped and bounded, toolAgeLabel is compact and deterministic, toolUsageTurns groups each turn without raw content, sessionMark is short, stable and never the session id.
