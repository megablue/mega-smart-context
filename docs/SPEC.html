mega-smart-context - behavior spec

User-visible behavior only: what the product does and what a user sees, readable without knowing the code. Behavior belongs here even when the code is where the reason for it lives. The reason, the mechanism and the traps live in docs/features/; process and hard rules live in AGENTS.md.

Scope

mega-smart-context is an OpenCode 2.0 CLI plugin that hands context management to the model. Instead of replaying the append-only transcript, every model request is rebuilt from three parts:

  1. the memory document the model wrote;
  2. a short working window of the newest turns, verbatim;
  3. the current turn.

The model is told what it owns and how to use it. It folds durable facts, decisions, files and open threads into memory, archives a turn it wants to keep, or purges one it does not. The plugin enforces the caps, keeps the current turn intact, and never edits the durable transcript.

It is for long agent sessions where replaying history grows without bound.

It deliberately does not:

  • edit the durable transcript; it rewrites only the request the host is about to send;
  • run a private model to summarize; there is no automatic semantic fold;
  • seed files, facts or a plan from observed tool calls; the model writes them;
  • protect the first user message; goal is the only guaranteed record of the request after the first turn leaves the window;
  • share memory between a parent and a subagent; every session is independent;
  • replace the host's compactor when memory is empty;
  • use a real tokenizer; every number is an estimate at charsPerToken.

What the model sees

Every request starts with a <smart-context> block:

goal: "..."
## Plan
- [active] 1. ...
## Facts
- "key": "value"
## Files
- "path": "what was done there"
## Decisions
- "name": "decision and why"
## Open
- "..."
## Refs
- docs/features/x.html#how-why - "gist" (~38 est; feature_map page:"x.html" section:"how-why")
## Notes
"..."
## Pending eviction
- u12 · "mechanical gist" · ~2.1k est
  -> smart_context action:"archive" turn:"u12" gist:"..." (or action:"purge" turn:"u12")

An empty goal renders an explicit warning. Values are JSON-quoted so a newline or a delimiter inside a model-written note cannot change the shape. The block is data, not instructions; the standing policy lives in the system message. It carries no live counters either: the running numbers are read on demand with smart_context { action:"stats" } or /context, so the block changes only when memory itself does.

The working window follows the block, verbatim, newest turns first in budget terms. The current turn is always kept, including every tool call and result the model just asked for.

Nothing the plugin does to a message in the window depends on a newer turn. An oversized tool result is shortened by a pure function of its own bytes, and reasoning is passed through exactly as the host sent it. A message therefore keeps the same bytes on every later pass, so a provider's prefix cache above it stays warm.

Host notices - the Plan/Build reminders the host injects as synthetic user messages, and the nudge it appends when a reply is cut off at the output-token limit - are not replayed as turns. The plugin strips them from the working window and pins every distinct text into the system prompt under "## Pinned host notices", newest first. "Newest" is recency of emission: a text the host re-emits moves to the end, so the refusal lands on the instruction that is actually live. A mode switch therefore cannot evict a turn, and the standing instruction survives every pass until a newer notice replaces it. The model may retire a superseded notice with smart_context { action:"notice", remove:"<id>" }; the newest is the live instruction and a removal of it is refused. A retirement outlives the pass that recorded it - the text stays retired while the host's window still holds a copy - and clears when the host emits the same text again under a new id.

Host messages split into a second class. A background job's completion (a <shell> or <subagent> block) arrives the same way a notice does, but it belongs to the turn that launched it: the plugin leaves it in the window, counts its bytes toward that turn, and starts no turn of its own, so a job finishing cannot age a pending eviction or show up as a working turn. The host's fixed one-sentence "The previous response was interrupted" continuation is a cue: the same tail treatment, but never pinned, because it is stale once the model has continued and is not a standing instruction.

What the plugin never counts is the host's own instruction set. Its core/instructions and neighbouring blobs ride in the request's system parts beside the policy, and no budget includes them: /context reports them as host system ~X est (N parts) for display only, and the line is absent when the host supplies no such part. When the build's debug option is on, the context pass also logs the count and the head of each such part, which is how the shape of event.system is checked.

The first turn and goal

On the first turn the current user message is visible. Once it leaves the working window it is gone; only goal survives. The policy tells the model to write the request into goal on the first turn, and the block shows goal: (empty ...) until it does. There is no protected first message and no automatic seed.

Budgets

Budget Default What it measures
memoryTokens 20,000 the rendered memory document, estimated
workingTokens 20,000 the verbatim working window, estimated
charsPerToken 4 the divisor that turns characters into estimated tokens
maxResultChars 4,000 one tool result larger than this is shortened head/tail

A tool result is shortened by keeping a head, a tail and a marker with the number of missing characters. The tool call and its result keep their ids and their order. A turn that alone exceeds the working budget is still kept; /context and action:"stats" report OVER CAP and the policy asks the model to fold sooner.

When the host reports a model context size, the plugin also warns when memory plus working would exceed 90% of it. It does not silently shrink either side.

Eviction and the archive

A turn that leaves the working window becomes pending. The model sees it under "Pending eviction" and chooses one of:

  • archive { turn, gist, keepRaw? } - store a one-line gist, and optionally the raw messages, in the cold archive;
  • purge { turn } - discard it permanently;
  • do nothing.

With autoArchive on (the default), an unhandled pending turn is archived after evictionLead new user turns, under a mechanical gist (the first line of its user message and its tools) and with its raw messages kept. The model can purge it later. With autoArchive off, an unhandled turn is dropped when the lead expires.

The archive is cold storage, not a second working set. smart_context with action:"recall" refuses unless the call includes lost:true; without it, the tool returns an instruction instead of results. recall matches every term of the query against the gist and the whole rendered turn, and each match carries short snippets with the character offset they sit at. expand { turn } returns the raw turn in pages of expandDigestChars characters (clamped by maxResultChars), ending with the exact range and continue with offset:N or end of turn; a negative offset counts from the end. mode:"outline" lists each part of the turn with its offset and size instead, which is how a reader finds the page worth opening. Without raw messages, expand returns the gist and says it is gist only. The archive is capped by archiveMaxTurns and archiveMaxChars, newest wins.

A delegate can read the archive of the session that spawned it: recall and expand accept from:"parent" (on by default, parentArchive:false turns it off). The field is read-only - every writing action refuses it - and the schema offers no other value. A delegated read ends by naming the reply budget: the caller keeps at most maxResultChars characters of the child's reply, so a long report must be written to a file and cited rather than returned.

Subagents

Every session - top-level or child - has its own memory, working window, pending turns and archive, keyed by session id. A child is detected by parentID. There is no inheritance in either direction; the only write bridge is the normal tool result when the child finishes, which the parent can fold into its own memory. The one read bridge is explicit: a child may pass from:"parent" to recall or expand to search the spawning session's archive, which it cannot write.

subagents: true (the default) applies the same transform to child sessions. subagents: false leaves child sessions untouched and passes their requests through unchanged.

Stored state

Each session's memory, pinned host notices, retired notices, pending turns and archive live in OpenCode's plugin storage, keyed by session id, and survive a restart. Deleting a session at /sessions does not notify the plugin, so the record would outlive it; on the next start the plugin asks the host whether each record's session still exists and removes the ones that are gone. A lookup that fails for any other reason keeps the record, and storage is shared by every project, so a record belonging to another project is left for that project's instance. The archive and the transcript text inside it are reclaimed when the record is removed.

Compaction

When the host asks for a checkpoint summary, the plugin returns the rendered memory document and skips the host's summarizer. If memory is empty, it declines and lets the host summarize; returning an empty block would erase the checkpoint in the name of owning it. The summary is the same block the model reads, so it too carries no live counters.

Undo

/undo in the terminal reverts the latest user message (or an earlier one) and the work that followed it: OpenCode stages the rollback, /redo cancels it, and the next prompt commits it by deleting the transcript from the boundary message onward. This plugin follows that commit. When the host emits session.revert.committed, the session record is rolled back on the next context pass: memory written in the undone turn is undone (the tool keeps an inverse journal of previous values), notices the model retired during it are pinned again, turns it purged are restored, pending turns created or auto-archived during it are dropped or pulled back, and the undone turns leave seenTurns, the archive and the pass history.

What the rollback cannot restore is stated so nothing is guessed at: an archive entry the caps trimmed, a pending turn whose raw messages are gone, and writes from turns older than the journal (the last eight turns, newest kept) are not reversible; /context reports last undo with a not restorable count when any applied. The memory block carries a ## Undo section for the turn after a rollback so the model distrusts its own pre-undo writes, and /context adds last undo and undo journal lines. A host without an event bus, and a transcript shortened by compaction, roll nothing back.

Feature-map references

smart_context { action:"ref", page, section, gist } stores a pointer plus the model's own one-liner. It reads the section from docs/features/<page> - the HTML page first, the Markdown page as a fallback - reports the gist and section costs, and tells the model which is shorter. The reference counts toward memoryTokens. A section that cannot be read is reported, but the pointer is still stored.

The update check

At most once every 24 hours the terminal half of the plugin compares the version it loaded with this repository's published package.json. When the published number is newer it shows one toast - 0.1.22 is available (installed 0.1.21) - git pull && npm run plugin:install - and stays quiet about that release until a newer one exists. Nothing about the check reaches the model: it adds no request part, no policy and no tokens, and every failure is silent. updateCheck: false in the config file stops both the request and the toast. A first install may need a restart before the terminal half is loaded.

The status dialog

The terminal half registers one palette command, Context status (id mega-smart-context.status; the id is the keybind key, and no default binding is claimed). Running it asks the server half for that session's numbers and opens a dialog: memory and working usage against their caps (a long turn is kept past the working cap by design, and the row says so), turns kept and dropped, pending/archive/reference counts, and the host system size when the last pass measured one. The status rows are not selectable, so the selection lands on the two actions.

Resume sends the same cue as /context resume through the host's synthetic channel: no user message, no new turn, and no pending eviction aged. Purge a turn… lists the pending and then the archived turns with their ids, asks for confirmation, and removes the chosen one from the record; the transcript is not touched, and the removal is journaled so /undo restores it. The list is re-read before it is shown, so a pass that archived or purged something in the meantime cannot leave a stale entry behind.

The numbers cross a process boundary: the terminal half's durable store is its own JSON file, not the server's KV, so the dialog reads the record over the host's plugin RPC (stats and purge). The pull happens when the command runs, never from a render path. With no open session the dialog says to open one; on a host without the RPC bridge, and on an RPC error, it says which of the two is missing instead of throwing. updateCheck:false does not remove the command.

The sidebar block

The terminal half also appends to sidebar.content - last inside the sidebar's scrollable list, not the panel's bottom edge - and draws the same reply as a short block: the build, a memory bar, a working-window bar (marked when it is over cap), turns kept and dropped, pending/archive/reference counts, and the host system size when a pass measured one. Gists, notice text and the archive list are deliberately absent: the block never grows with the session, and the dialog is where those are asked for.

Under the block are three words that act: [status] opens the dialog, [resume] asks and then sends the resume cue, and [purge] opens the purge list and its confirmation. Mouse clicks are optional: every action is still reachable from the palette command.

The block renders from an ephemeral per-session mirror that a pull fills: once when the session is shown, once after each idle pass, and again after a purge. At most one pull per session is in flight, a pull inside fifteen seconds is skipped, and the mirror keeps the thirty-two most recently read sessions. The render path never calls the RPC. A host without the slot API or without the JSX runtime keeps the dialog and reports sidebar: unavailable in it; sidebar:false turns the block off entirely.

The model surface

smart_context actions:

Action Effect
read { key? } print one memory key, or the whole document
patch { patch } merge a patch; maps merge, lists replace, null resets a key or deletes one map entry
stats memory, working, pending and archive usage
ref { page, section, gist } store a feature-map pointer and compare costs
archive { turn, gist, keepRaw? } move a pending turn to the archive
purge { turn? | query? } delete a pending or archived turn, or matching entries
recall { query, lost:true, limit?, from? } search the cold archive; refuses without lost:true. Every term must match, and each match carries snippets with their char offsets. from:"parent" searches the spawning session's archive instead, read-only, and names the caller's reply budget
expand { turn, mode?, offset?, limit?, from? } read an archived turn back as one honest page ending in its char range and how to continue; mode:"outline" lists each part with its offset and size. from:"parent" reads the spawning session's
notice { remove? } list the pinned host notices - a mode switch or an output-limit nudge - or retire a superseded one by id; the newest is refused, and a retirement holds until the host emits that text again under a new id

The /context command prints the same state for the user:

Command Effect
/context or /context status memory, working, pending, archive, goal, the host system size, and the loaded build's version
/context now archive every pending turn now
/context resume start a model turn with the plugin's resume cue through the host's synthetic channel - no user message, no new turn, and no pending eviction aged
/context memory <key> print one memory key
/context recall <query> search the archive as the user
/context purge <turn> delete a pending or archived turn

/context resume is the one command that starts a model turn instead of printing: it admits RESUMED_TEXT as a synthetic user message with resume: true, and the context pass classifies that sentence as a cue, so it stays in the window, counts toward the turn it continues, and ages no pending eviction.

The same output reports a rollback when one has been applied - last undo: before <turn> · N memory key(s) restored, M turn(s) dropped, with a not restorable count when the journal could only do part of the job - and the journal itself as undo journal: N turn(s), oldest <turn> · /undo rolls these back.

The version is MAJOR.MINOR.PATCH: MAJOR.MINOR is the released line, and PATCH is the number of commits since the base recorded in package.json, so it advances with every commit and the README version badge follows the same field. What /context prints is the loaded build's own version, which lags the repository until the install is re-synced.

Settings

Every setting is read from four layers, most specific last: built-in defaults, the package options.json, the plugin options, and ~/.config/opencode/mega-smart-context.json. The user file is created with every default on first run and never overwritten. A source replaces only the keys it sets. An unknown key or a wrong type is an error: the plugin refuses to load rather than silently keeping a default the user believes they replaced.

Setting Default Range Where
enabled true bool - master switch config file
memoryTokens 20000 >= 1000 - memory cap, estimated config file
workingTokens 20000 >= 500 - working window cap, estimated config file
charsPerToken 4 2..8 - estimation divisor config file
subagents true bool - manage child sessions independently config file
evictionLead 1 0..20 - new user turns a pending turn is shown before auto-archive/drop config file
autoArchive true bool - archive unhandled evictions config file
archiveMaxTurns 200 0..5000 - archived turns per session config file
archiveMaxChars 400000 >= 10000 - archived characters per session config file
parentArchive true bool - allow from:"parent" on recall/expand config file
expandDigestChars 4000 >= 500 - characters per expand page, clamped by maxResultChars config file
refs true bool - offer the ref action config file
maxResultChars 4000 >= 200 - per-result erosion limit config file
manualCommand true bool - register /context config file
updateCheck true bool - ask GitHub once a day for a newer published version and toast once per release; no request and no toast when false config file
sidebar true bool - draw the block in the terminal's sidebar; when false no slot is claimed and no mirror is kept config file
debug false bool - log pass decisions to stderr config file

The environment overrides are for tests and unusual installs: MEGA_SMART_CONTEXT_CONFIG points at a different user file, and MEGA_SMART_CONTEXT_NO_USER_CONFIG=1 skips the user layer entirely.

Out of scope

  • No cross-session or shared memory.
  • No automatic semantic summarization, file seeding or plan seeding.
  • No protected first user message.
  • No exact tokenizer or per-model token accounting; the caps are estimates.
  • No transcript edits; host compaction remains the only thing that writes a checkpoint, and this plugin owns that checkpoint only when memory is non-empty.
